## Findings

### Blocker — active wait and opt-out restrictions do not override approval

The validator enforced only terminal `do_not_contact`, not active person/relationship/opportunity wait or recipient opt-out. Exact approved outreach passed each condition.

**Impact:** A portable record can become eligible for a separate external handoff while an authoritative communication boundary says pause or opt out.

**Smallest acceptance condition:** Reject approval when an applicable recipient, relationship, or linked opportunity has active wait, or recipient consent is opted out, until the controlling state changes through an accountable decision. Add exact-approval negative tests.

### Blocker — type-confused recipient references bypass person boundaries

`recipient_person_id` used a generic stable ID, and graph validation enforced record type only for evidence fields. An organization ID passed as the exact approved recipient, avoiding person consent and restriction checks. The same weakness affected accountable-person and owner references.

**Smallest acceptance condition:** Add type-aware graph validation for semantically typed references, at minimum recipient, deciding person, participant/person, contribution, opportunity, and owner IDs. Add negative tests using an existing ID of the wrong type.

### Material — required baseline and candidate identity are absent from the PASS report

Baseline comparison ran only when the optional argument was supplied. The generated report recorded version and command but no candidate source identity, baseline state, or baseline identity. A no-baseline full run wrote `Overall: PASS` without disclosing the skipped release requirement.

**Smallest acceptance condition:** For release assurance, require a nonempty authoritative baseline and record its stable identity/hash. Record a reproducible candidate source identity and clean/dirty state. Without a baseline, report the comparison as explicitly not run or deferred.

### Material — portable records omit the canonically required framework version

Canonical implementation guidance required schema and framework version on each portable record, but the common schema and all examples recorded only schema version.

**Smallest acceptance condition:** Add required `framework_version` provenance with migration and acceptance coverage, or amend the higher-authority canonical requirement and explain the alternative compatibility mechanism.
