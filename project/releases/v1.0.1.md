# Influence Operating Framework v1.0.1

- **Release date:** 2026-08-22
- **Type:** Patch, documentation and repository maintenance
- **Previous release:** [v1.0.0](https://github.com/BradGroux/influence-operating-framework/releases/tag/v1.0.0)

## Summary

Version 1.0.1 adopts Open Framework Commons v1.1.0 and corrects validation in
shallow Git clones. The release changes no canonical Influence framework
meaning.

## Commons adoption

Influence adopts the Commons v1.1.0 annotated tag object
`79e5f06dab46f262cad1d1daf7840e683ffc3880`, which peels to release commit
`f25a2b89b4aed95984fd235e2e229efe52c125d8`.

The nine shared principles and research guidance are unchanged from Commons
v1.0.0. The relevant boundary change recognizes Focus Operating Framework as
the fifth equal, independent product and includes it in future
shared-applicability review. Influence retains independent authority over its
concerns, method, terminology, examples, research, governance, roadmap,
implementation choices, and releases.

[Decision 0004](../../decisions/0004-adopt-open-framework-commons-v1.1.0.md)
records the local adoption, deferrals, and no-deviation disposition.

## Validation correction

A depth-1 clone previously produced 194 false errors because unavailable
reviewed commits triggered repeated path and line-range failures. Validation
now keeps current-tree and reachable-history checks active, reports unavailable
historical evidence once, and directs release work to restore complete history
with `git fetch --unshallow`.

Full clones still treat a missing reviewed commit or invalid historical citation
as a failure. The primary release workflow continues to use complete history,
and a separate CI check covers the shallow-clone path.

Historical citations to underscored script filenames remain unchanged because
those names are correct at their exact reviewed commits.

## Compatibility and limits

This is backward-compatible repository and governance maintenance. It does not
change the six concerns, seven practice moves, responsible-practice standard,
measurement guidance, glossary, or examples.

Shallow-clone success establishes current-tree integrity and reachable-history
coverage only. Complete historical assurance requires complete Git history.
Repository checks do not establish real-world, organizational, legal, ethical,
accessibility, professional, or domain validation.

## Release verification

The release process requires:

- the full repository gate, including all historical review evidence and eight
  Mermaid diagrams;
- the depth-1 clone regression check and explicit partial-history reporting;
- exact-candidate standards and specification review;
- passing pull-request and merged-main checks;
- an annotated `v1.0.1` tag resolving to the verified merged commit; and
- published GitHub release readback through the steward's authenticated
  account.
