# Influence Operating Framework v1.0.2

- **Release date:** 2026-08-22
- **Type:** Patch, release-integrity maintenance
- **Previous release:** [v1.0.1](https://github.com/BradGroux/influence-operating-framework/releases/tag/v1.0.1)

## Summary

Version 1.0.2 adds cryptographically verified release identity and makes
complete Git history mandatory for release validation. It changes no canonical
framework meaning and does not rewrite v1.0.1.

## Signed release identity

Release tags use a dedicated Ed25519 signing key registered with GitHub. The
repository tracks only the public key in
`.github/signing-keys/allowed-signers`; the private key remains outside the
repository with restrictive local permissions.

Public signing-key fingerprint:
`SHA256:EKmFG8TU58Rz+2TGF/Wu4N3PmLu2+zcNFhhKhvI9k3Q`.

The release gate requires an annotated version tag, verifies its signature
against the tracked public key, and requires the tag to resolve exactly to the
checked-out release commit. GitHub verification and public tag-object readback
remain separate publication checks.

## Complete-history release assurance

Ordinary repository validation remains useful in shallow clones and labels
historical coverage as partial. Release validation is stricter: it refuses a
shallow repository, requires a clean worktree, and runs the complete repository
and Mermaid gates before any tag-specific checks.

This separates contributor feedback from release assurance. A partial clone can
still detect current-document defects, but it cannot authorize a release.

## Compatibility and limits

This release changes repository stewardship only. It does not change the six
concerns, seven practice moves, responsible-practice standard, measurement
guidance, glossary, examples, or Open Framework Commons v1.1.0 adoption.

Signature verification establishes control of the registered signing key. It
does not prove real-world framework effectiveness or human, organizational,
legal, ethical, accessibility, professional, or domain validation.

## Release verification

The release process requires:

- complete-history repository validation and Mermaid rendering;
- explicit rejection of release validation in a depth-1 clone;
- successful ordinary depth-1 validation with partial-history reporting;
- exact-candidate repository-standards and issue-requirements reviews;
- passing pull-request and merged-main workflows;
- a signed annotated `v1.0.2` tag verified locally and by GitHub; and
- public tag, release author, release body, and version readback.
